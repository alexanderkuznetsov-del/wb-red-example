# wb-red-example

Черновик — пример резервированной пары контроллеров Wiren Board (active/standby) с общими Modbus-модулями через один шлюз WB-MGE. Собрано и проверено живьём на паре 192.168.143.111/112 через МГЕ 192.168.143.113.

Это не готовый продукт и не официальный пример Wiren Board — рабочий черновик конкретной инсталляции, выложен для ссылки из статьи на вики. IP-адреса, приоритеты и имена устройств — из этой конкретной установки, при переносе на другую пару заменить под себя.

## Архитектура

- Оба контроллера независимо и одновременно опрашивают одни и те же Modbus-устройства за общим МГЕ.
- Активный/резервный статус определяет `keepalived` (VRRP, unicast — оба узла на WiFi, не Ethernet).
- Здоровье для VRRP — не «жив ли Linux», а жива ли сама автоматика (`wb-rules`, `wb-mqtt-serial`) и виден ли общий МГЕ.
- Чтение разрешено всегда, с обоих узлов. Запись в устройства — только с активного, через общий wb-rules модуль `wbha.js`, а не разбросанными по коду проверками.
- Роль/VIP/приоритет публикуются в MQTT и видны через отдельное виртуальное устройство в вебе каждого контроллера.

### Особенности, характерные для случая подключения по Wi-Fi

Эта конкретная пара связана по Wi-Fi, а не по Ethernet, и две настройки в `keepalived.conf` — прямое следствие именно этого:

- **`unicast_src_ip`/`unicast_peer`** вместо мультикаста по умолчанию — точка доступа Wi-Fi часто режет мультикаст-трафик между клиентами. В проводной сети обычно можно оставить VRRP на мультикасте.
- **`dont_track_primary`** — без неё `keepalived` уходит в `FAULT` при любом кратковременном дребезге интерфейса (переассоциация Wi-Fi) и не восстанавливается сам. На Ethernet-линке такого дребезга обычно нет.

Если переносите пример на проводное подключение — обе настройки стоит пересмотреть, а не копировать вслепую.

## Структура репозитория

```
keepalived/
  keepalived.conf.111     — конфиг VRRP для узла с priority 150 (master по умолчанию)
  keepalived.conf.112     — конфиг VRRP для узла с priority 100 (backup по умолчанию)
  override.conf           — systemd drop-in: ждать стабильный IP перед стартом keepalived
scripts/                  — /usr/local/bin/ на обоих узлах
  wb-ha-healthcheck.sh    — health-check для vrrp_script (автоматика + доступность МГЕ)
  wb-ha-notify.sh         — публикует роль/VIP/приоритет при смене VRRP-состояния
  wb-ha-role-heartbeat.sh — подстраховка: переопубликовывает роль раз в минуту (cron)
  wb-ha-wait-for-ip.sh    — ждёт стабильного присутствия IP перед стартом keepalived
mosquitto/
  000persistence.conf          — retained-сообщения переживают рестарт брокера
  wb-ha-bridge.conf.example    — пример bridge для синхронизации уставок (стадия 2, опционально)
wb-rules/
  wbha.js                   — модуль арбитража записи по роли (на обоих узлах, без правок)
  wb_ha_status.js           — виртуальное устройство-дашборд (на обоих узлах, без правок)
  motion_light.js           — пример реальной автоматики, использующей wbha.dev()
  setpoint_sync_template.js — шаблон синхронизации уставки между узлами (стадия 2, опционально)
```

`wb-ha-notify.sh` и `wb-ha-role-heartbeat.sh` содержат константу `PRIORITY` (150 на узле с бо́льшим приоритетом, 100 на другом) — она должна совпадать со значением `priority` в `keepalived.conf` этого же узла. `wb-ha-wait-for-ip.sh` содержит свой IP на каждом узле. `wbha.js`, `wb_ha_status.js` — идентичны на обоих узлах без изменений.

## Порядок установки (кратко)

1. `apt-get install -y keepalived` на оба узла.
2. Разложить `keepalived.conf.*` → `/etc/keepalived/keepalived.conf` (свой файл на каждый узел), `override.conf` → `/etc/systemd/system/keepalived.service.d/override.conf`.
3. Скрипты из `scripts/` → `/usr/local/bin/`, права `root:root 755`.
4. `mosquitto/000persistence.conf` → `/etc/mosquitto/conf.d/`.
5. `wb-rules/wbha.js` → `/etc/wb-rules-modules/`, остальные `.js` из `wb-rules/` → `/etc/wb-rules/`.
6. Перезапустить `keepalived`, `mosquitto`, `wb-rules` на обоих узлах.
7. Проверить реальными тестами (не чтением конфигов) — см. «Проверено живьём» ниже.

## Подтверждённые живыми тестами тайминги

- Полное исчезновение узла из сети (питание/WiFi off) → резерв подхватывает роль за ~3 секунды (чистый протокол VRRP).
- Деградация автоматики при живом Linux (`systemctl stop wb-rules`) → ~8 секунд до перехода соседа в master, без пересечения «оба active» (переход синхронный, разница <10 мс по логам `keepalived` с обоих узлов).
- Восстановление автоматики → возврат роли исходному узлу за ~2.4 секунды (`preempt_delay 5`).
- Две перезагрузки обоих узлов подряд — ни разу `FAULT`.
- Узел с деградировавшей сетью до МГЕ (но формально «живыми» службами) — проверка в `wb-ha-healthcheck.sh` корректно отдаёт роль соседу.

## Известное непокрытое ограничение — сплит-брейн

Если связь рвётся именно **между двумя узлами пары** (а не у одного из них с остальной сетью), и МГЕ при этом одинаково доступен обоим — **оба узла становятся `active` и оба держат VIP одновременно**. Подтверждено живым тестом (`iptables` между узлами). Это фундаментальное ограничение двухузловой VRRP-пары без третьего арбитра/witness — `dont_track_primary`, `preempt_delay`, проверка доступности МГЕ от него не защищают, потому что в этот момент оба узла считают себя единственным выжившим.

После снятия блокировки восстановление полностью автоматическое, без `FAULT`.

Рабочих вариантов закрыть это два (не реализованы):
- арбитраж записи в `wbha.js` по дополнительному независимому каналу между узлами (не через VRRP-приоритет — попытка через `vrrp_script`/`weight` не работает, `keepalived` продвигает backup в master по таймауту безусловно, приоритет тут не участвует);
- прямая остановка `keepalived` на резервном узле при обнаружении, что активный узел всё ещё жив по независимому каналу.

Переход основного VRRP-линка с WiFi на проводной Ethernet в топологии «звезда» через коммутатор не устраняет проблему теоретически, но ощутимо снижает вероятность именно избирательного разрыва «вижу всё, кроме соседа» на практике.

## Не реализовано осознанно

- Резервирование самого МГЕ — единая точка отказа и для чтения, и для управления с обеих сторон.
- Репликация состояния автоматики (таймеры/счётчики `wb-rules`) при отказе — переинициализируется с нуля.
- Синхронизация персистентных уставок между узлами — механизм продуман и проверен (`setpoint_sync_template.js` + `wb-ha-bridge.conf.example`), но под конкретную уставку не применялся.
